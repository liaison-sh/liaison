# Native platform projects

Both native projects are generated by the Capacitor CLI and then COMMITTED: the edits below live
in generated files, so a regeneration would silently drop them and the tests in
`ios-config.test.ts` / `android-config.test.ts` are what says so.

## iOS

Generated with `bunx cap add ios` (Capacitor 8.5.2). Verified on this machine:

- **No CocoaPods.** Capacitor 8 resolves plugins through Swift Package Manager: the generated
  project carries `ios/App/CapApp-SPM/Package.swift` and there is no `Podfile`. `cap add ios`
  completed with no pod install step and no CocoaPods installed on the machine.
- `PRODUCT_BUNDLE_IDENTIFIER` is `sh.liaison.mobile`, written from `capacitor.config.ts`'s
  `appId`. The display name comes from `appName`.
- `Info.plist` declares `CFBundleURLTypes` with the single scheme `liaison`, so the OS hands the
  app `liaison://thread/<id>` and `liaison://connect?server=...`. The desktop shell claims the same
  scheme; the two are told apart by the link's host, never by the scheme.
- `ios/App/App/public` (the copied apps/web build, `apps/web/dist-native`) and `capacitor.config.json` are generated on
  every `cap sync` and are ignored by the project's own `.gitignore`.

### Entitlements, push and privacy

`App/App.entitlements` carries `aps-environment` only, wired into both build configurations
through `CODE_SIGN_ENTITLEMENTS`. It says `development`; Xcode rewrites it to `production` when it
exports for TestFlight or the App Store. There are no associated domains and no universal links on
either platform: an association file has to be served from each operator's own host, and a domain
in the entitlements is baked into a binary every fork ships. Links into the app use the `liaison`
scheme and push taps.

- `AppDelegate.swift` forwards the APNs token (and a registration failure) to Capacitor through
  `.capacitorDidRegisterForRemoteNotifications` / `.capacitorDidFailToRegisterForRemoteNotifications`.
- `LiaisonNativePlugin.swift` is a local plugin in the App target, registered by
  `MainViewController` (the window's root, a `CAPBridgeViewController` subclass). JS side:
  `src/native/liaison-native.ts`. `apsEnvironment()` reads `aps-environment` from
  `embedded.mobileprovision` (no profile: `production`; simulator: `sandbox`), so the server sends
  each token to the matching APNs host. `authenticate({url, callbackScheme})` runs
  `ASWebAuthenticationSession` and resolves the callback URL.
- `PrivacyInfo.xcprivacy` declares no tracking, UserDefaults (CA92.1, used by
  `@capacitor/preferences`) and the collected data types (email, name, user content, device id).
- `UIRequiredDeviceCapabilities` is `arm64`.

## Android

Generated with `bunx cap add android` (Capacitor 8.5.2). NOT built here: this machine has no
Android SDK and no JDK, so `./gradlew assembleDebug` was never run and nothing is claimed about it.
`cap add android` only generates files and needs neither.

- The application id is `sh.liaison.mobile`, written into `android/app/build.gradle` from
  `capacitor.config.ts`'s `appId`.
- `AndroidManifest.xml` carries a second `<intent-filter>` on the main activity for
  `android:scheme="liaison"`, with `VIEW` plus the `DEFAULT` and `BROWSABLE` categories, matching
  the iOS scheme. The generated `MAIN`/`LAUNCHER` filter is left alone.
- `MainActivity` registers one local plugin, `LiaisonAuthSession`
  (`LiaisonAuthSessionPlugin.java`), the Android side of `authenticate` in
  `src/native/liaison-native.ts`: it opens a sign-in or app-connection page in the system browser
  and resolves the `liaison://oauth-complete` link the browser hands back (the activity is
  `singleTask`, so the link arrives through `onNewIntent`). Coming back to the app without that
  link rejects with code `cancelled`. Any app may claim the scheme, so the link is worthless on its
  own: its code is redeemed only with the PKCE verifier the page kept. Checked only against the
  Capacitor and Android API signatures (`javac` with stubs), never run on a device.
