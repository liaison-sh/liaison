# SDK gap log

When `@liaison/app-sdk` can't express something an app genuinely needs, the
rule (per `docs/app-development.md` §11) is: **extend the SDK, don't reach
around it.** This log tracks each gap as it's found — what hit the wall, why
a workaround wasn't taken instead, and the current status.

| Gap | Found by | Why the SDK doesn't cover it | Resolution / status |
|---|---|---|---|
| Raw DB connections (arbitrary socket-level access to an external database) as a first-class app/connection type | `database` connector (`apps/api/src/apps/database/`) | QuickJS-sandboxed apps have no socket primitive — `ctx.fetch` is HTTP-only and domain-allowlisted, so a Postgres wire client can only run host-side. There is no `AppContext` primitive for "this app needs a raw DB connection"; every existing connection type (`credentials`, OAuth) assumes the app's own handler code talks to it, which sandboxed apps structurally cannot do for a non-HTTP protocol. | **Workaround taken, not a bypass:** the `database` connector is built as an in-tree, host-side **bridge-extension** app (`trusted:false`, gitlab/google-drive shape) — sandboxed `handlers.ts` delegators call into a host-side `bridge.ts` that owns the actual DB connection; the sandbox itself never touches credentials or a socket. This is within the existing SDK's sanctioned escape valve (bridge extensions), not a sandbox bypass. If a **third** connector needing raw DB/socket access shows up, consider promoting "declared raw connection, host-mediated" to a first-class `connections.<name>.type` (e.g. `"database"` or `"tcp"`) so future connectors don't each hand-roll their own bridge-extension wiring — currently deferred since one bridge-extension precedent (gitlab) plus this one (database) hasn't yet shown enough repetition to justify the SDK surface. |
| Webhook signing secret for a webhook-ONLY app (no outbound connection) | `monitoring` app (`bundled-apps/monitoring/`) | The only way the kernel mints a webhook signing secret readable by a sandboxed verifier (`bridge.config_get`) is `connections.<name>.webhookSecretConfigKey` — and the mint fires **when the connection is established**. Monitoring never calls out to its alert sources (deliveries are inbound-only, `ctx.fetch` unused), so there is no natural connection to declare; the manifest cannot say "this app receives signed webhooks, mint me a secret at install/grant time". | **Workaround taken, not a bypass:** monitoring declares a minimal `credentials` connection (`alert-source`, one free-text `label` field, empty `allowedDomains`) purely so connecting mints `monitoringWebhookSecret`; the operator reads it back via the admin-scoped `webhook_info` tool and pastes it into the alert source's outgoing-webhook config. Entirely within the sanctioned connection surface, but the "connect a pseudo-credential to obtain a secret" step is ceremony. If a second inbound-only app appears, consider a first-class manifest declaration (e.g. `webhooks.<topic>.secretConfigKey` minted at install/scope-grant time) so webhook-only apps skip the dummy connection. **Repetition count: now THREE instances** — `projects`' `ci-source` connection (`ciWebhookSecret`) was the 2nd and `calls`' `transcript-source` connection (`callsWebhookSecret`) the 3rd, each an identical dummy `credentials` connection + `webhookSecretConfigKey` + admin `webhook_info` read-back. The pattern is stable and copy-paste cheap, so still not blocking, but three repetitions is the usual threshold where the first-class declaration starts paying for its schema surface. |
| Operator-configured service host reachable via `ctx.fetch` (dynamic fetch allowlist) | a single-customer `kpi` app (not in this repository) | The sandbox fetch layer (`rpc-bridge.ts` `validateSandboxFetchUrl` + `lib/outbound-fetch.ts`) enforces a **static** manifest domain allowlist, HTTPS-only, and a private-network block (literal-IP + DNS-resolved). The kpi app's `kpi-service` credentials connection carries an operator-entered `baseUrl` — a host unknowable at manifest-authoring time — and the natural deployment shape is a same-compose sidecar (`http://kpi-service:8787`), which trips all three rules. OAuth `templateVars` solve the dynamic-host problem for OAuth connections (`*.myshopify.com`), but there is no credentials-connection equivalent, and no posture at all for same-stack private services. | **Open (kernel unchanged) — deployment-shape workaround shipped:** the kpi manifest now allowlists `*.sslip.io` (the generic wildcard-DNS TLS-fronting convention) and deployments front kpi-service behind their TLS proxy (e.g. Caddy `https://<public-ip>.sslip.io/kpi/*` → loopback kpi-service). The grant is exercisable only by the app's own handlers (they fetch the operator-entered `baseUrl` exclusively — the agent cannot direct fetches), and the DNS-resolved private-net block still rejects `*.sslip.io` names resolving private. Non-sslip deployments must still bake their own hostname into the allowlist at image build, so the gap stands. Candidate SDK fixes: (a) connection-derived allowlist entries — a `credentialFields` entry flagged `host: true` whose connect-time value is added to the app's fetch allowlist; (b) a `network.allowPrivateHosts` posture grantable by the operator (not the manifest) for first-party/in-image apps talking to same-stack sidecars. |
| Deliberate, user-actionable error messages from sandboxed (untrusted) tool handlers are redacted in production | `kpi` app live e2e on staging | `execute-tool.ts` hides untrusted-handler throw messages behind an opaque `"Tool execution failed"` in production (`isUntrustedProd`, no-leak rule) — correct for accidental internals, but it also swallows errors an app *authored for the caller*: kpi's `"kpi-service rejected the bearer token (401) — update the kpi-service connection token"` reaches only the server log (`innerMessage`), never the agent, so the agent can't distinguish bad-token from service-down. Even the typed-status path (numeric `status` on the throw) is overridden by `isUntrustedProd`. | **Open — observation, no workaround.** Kernel security posture deliberately untouched. Candidate fix: an SDK-blessed "public error" channel — e.g. a `ToolUserError` class (or `{ error: { public: true } }` marker) whose message is explicitly caller-safe and survives redaction, keeping accidental throws opaque. |
| A cross-app callRef→document read that only ever resolved through the search index (Meilisearch), with no DB-backed exact-lookup alternative (same shape as a still-open `collections_list`-class gap: no name-idempotent lookup exists for knowledge collections either) | `calls` connector's `calls_segments_since`/`calls_list` | Every existing callRef→doc resolution rode `knowledge:search` exclusively (`resolveCallDocId`) because no DB-backed exact-title READ tool existed — `findOrgDocByTitle` (`apps/api/src/apps/knowledge/service.ts`) is the closest precedent but is **write-scoped**, feeding only the `knowledge_create` upsert-redirect guard, not exposed as an agent-callable read. Under staging replay load the app-side Meilisearch indexing pipeline lagged behind a poll window while the doc provably existed in Postgres (`knowledge:update` revision-conflict retries visibly hitting it in the app logs), producing spurious `call_not_found` 500s: a real discovery-robustness gap, not a flaky test. | **Closed.** Added `findDocByTitle` (`apps/api/src/apps/knowledge/service.ts:547`) — the READ-scoped sibling of `findOrgDocByTitle`, gated through the same `loadDocumentShareRole` + `assertCanReadDocumentRow` path `get` already uses (not the write-guard) — exposed as a new agent-visible tool `knowledge:find_by_title` (`apps/api/src/apps/knowledge/app.manifest.json:613`; exact title, DB-backed, `includeArchived` opt-in, returns `{id, revision, title, archived}` or `found:false`). The `calls` app's `resolveCallDocId` (`bundled-apps/calls/src/tools.ts`) now tries `find_by_title` FIRST and only falls back to `knowledge:search` when the `find_by_title` call itself errors (a clean `found:false` is trusted as genuine, never triggering the fallback) — declared in the calls manifest's `cross_app_calls`. This is also the first general-purpose DB-backed exact-lookup READ tool in the estate; it is a name-idempotent read precedent any future "does X with this exact name already exist" need (including the still-open `collections_list`-class gap for knowledge collections themselves) can now point at instead of re-deriving from scratch. Scope-gate caveat: cross-app callers hold scopes in WILDCARD form (`knowledge:*`), so the handler's gate uses the wildcard-honoring `hasScope`, never a literal `scopes.includes()`. |
| Per-call custom headers on `ctx.fetch` — investigated for the `ads` app's Google Ads arm, confirmed NOT a gap | `ads` app (`bundled-apps/ads/`), Google Ads REST client | Google Ads REST requires a `login-customer-id` header on every call (and took a `developer-token` header until Google retired developer tokens on 2026-09-09; the client no longer sends it), in addition to the OAuth Bearer token. Verified `AppContext.fetch(url, {method, headers, body})` (`packages/app-sdk/src/types.ts:100`) already accepts an arbitrary `headers` record, and `meta-client.ts` already sets `Authorization` this way — so arbitrary per-call headers are fully expressible today. | **Not a gap — recorded so a future reader doesn't re-investigate.** No SDK change made or needed; `google-client.ts` sets `Authorization` and `login-customer-id` via the existing `headers` param. |
| OAuth2 connections cannot carry operator-entered config alongside the token | `ads` app (`bundled-apps/ads/`), Google Ads + Merchant Center arm | Google Ads REST needs an OAuth token (for the `google` connection) PLUS operator-entered strings the API requires on every call (MCC login-customer-id, operating customer id, Merchant Center id; formerly also a developer token) that OAuth cannot hold. Verified: the OAuth callback (`service.ts:1525`) stores ONLY access/refresh tokens; the `/credentials` POST route (`connections/routes.ts:158`) rejects non-credentials connections; `getCredentials()` on an oauth2 connection returns `{}` per the SDK contract. So an app needing "OAuth token + a few operator-entered strings" must declare a SECOND `credentials` connection as a config vault — there is no single-connection way to pair the two. | **Workaround taken, not a bypass:** the `ads` app pairs a `google` oauth2 connection (tokens only) with a `google-config` credentials connection (the Google Ads/Merchant config strings), read via the existing `getCredentials()` path (`get-client.ts`'s Meta resolver already does the analogous dual-shape normalization, mirrored in `google-config.ts`). Candidate first-class SDK fix if a second such app appears: allow `credentialFields` on an oauth2 connection to be collected at connect time and stored in `credentialsEncrypted` alongside the tokens, readable via `getCredentials()` — the storage column and the read path already exist; only the connect-form collection + callback persistence are missing. Deferred (one instance so far). |
| `ctx.db.findMany`'s `where` clause supports ONLY flat equality (`col = val`, or `IS NULL` for a null value) — no comparison operators (`>=`, `>`, `<`, `<=`, ranges) | `ads` app (`bundled-apps/ads/`), `google_pause`'s bulk-pause blast-radius check | The bulk-pause threshold needs "campaign-level pauses in the last rolling hour" — a `created_at >= since` predicate. Verified in `apps/api/src/modules/apps/sandbox/rpc-bridge.ts` `buildWhereClause` (lines ~767-790): every `where` entry becomes `col = val` (or `IS NULL` when `val === null`); there is no operator-object shape (`{gte: ...}` etc.) recognized anywhere in the bridge. So the temporal cutoff cannot be pushed into the `where` clause at all today. | **Open — workaround taken, not a bypass:** `google_pause` fetches all `pause_ledger` rows matching the flat equality filter (`object_type`, `paused_by_us`) and applies the `created_at >= since` cutoff as an in-memory `Array.filter` afterward. Fine at pause_ledger's expected volume; would need revisiting if the table grows unbounded. Candidate first-class SDK fix if a second time-windowed query need appears: an operator-object `where` value shape (`{gte, gt, lte, lt}`) recognized by `buildWhereClause`/`validateWhereFields`, mirrored in the sandbox `db_findMany` zod schema. Deferred (one instance so far). |
| A deployment's database-connector catalog (curated read definitions for the `database` app, operated outside this repo at the infrastructure level) may not yet have a curated read for a table or join an app needs, so app-side code must degrade gracefully rather than assume the read exists. | `ads` app's consent-join (`src/lab/consent-join.ts`), metrics inputs (`src/metrics/inputs.ts`), and erasure sweep (`src/lab/audience-erasure-consumer.ts`) | The database-connector catalog is deployment infrastructure, not part of this repo, and is edited as a deliberate ops change independent of any single app's release. An app that needs a new curated read (e.g. an email-joined purchase-attribution view, a marketing-consent join, or a pending-erasure poll) cannot assume the ops-side catalog has been updated to match, and must not block on it. | **Open — fallback taken, not a bypass.** Call sites try a preferred curated `database:db_read` name first and fall back to `database:db_query` with a parameterized SELECT when the curated read errors, so every hub-DB read degrades to an actionable `unavailable`/stale lineage flag (metrics) or a fail-closed drop (consent-join) rather than crashing. Closing this gap for real requires an ops-side change: add the missing curated reads to the deployment's database catalog, resolve any needed join keys, and regenerate the read-only DB grants. That step is deliberately left to deployment/ops, not bundled into an app-only implementation pass. |
| `audience_erasure_sweep`'s transport is POLLING an external system's DB (via `database:db_read`/`db_query`) rather than a push/webhook, and Liaison cannot mark a row in that external system's event outbox as consumed, so consumption state instead lives in a new Liaison-side table (`audience_erasure_log`). | `ads` app's audience-erasure consumer (`src/lab/audience-erasure-consumer.ts`) | Liaison cannot subscribe to an external, separately-deployed system's in-process event bus. There is no shared process to hook into, and there is no push/webhook transport in the SDK for consuming another system's outbox, so an app must either poll or wait on an inbox endpoint that doesn't exist yet on the other side. | **Workaround taken, not a bypass.** Polling via the existing `database` cross-app is the already-available transport; the Liaison-side `audience_erasure_log` (keyed by `email_sha256` + platform) makes repeat sweeps idempotent regardless of which side "owns" consumption truth, since a removal is also a harmless no-op on Meta/Google if repeated. If the external system later exposes a proper inbox endpoint (an outbox-consumer webhook, or an API marking its own events consumed), `audience_erasure_sweep`'s poll call is the one place to swap the transport; the removal logic (Meta DELETE /users, Google offlineUserDataJobs) is unaffected either way. |
| No app-facing "list MY app's own pending approvals" read tool existed in `@liaison/app-sdk` — a sandboxed app could not query `kernel.approval_requests` scoped to itself. | `ads` app dashboard (`src/ui/Dashboard.tsx`, pending-approvals panel) | The only approvals-listing surfaces were host-internal: `apps/web/src/modules/approvals/approvals-service.ts` (`listDecidableByMe`/`listBundle`, frontend-only, imports the kernel API client directly) and the kernel attention-provider registration (`apps/api/src/modules/apps/init.ts`, `scope:"kernel:approvals:read"`, host-side handler path `../approvals/attention.ts`) used for the Home inbox badge. Neither was reachable from a sandboxed app's `AppContext`. | **Closed.** The kernel bridge now exposes a sandbox-callable approvals read: `kernel_listApprovals` (`apps/api/src/modules/apps/sandbox/rpc-bridge.ts:1237`), RLS/org-scoped to the calling app. `pending_approvals_list` is a fully implemented tool in the `ads` app (`bundled-apps/ads/src/reads.ts:647`) built on this affordance, and `invoicing` (`bundled-apps/invoicing/src/handlers.ts`) already consumes the same bridge call via its own `pendingApprovalsList`, so two apps now share the pattern. Remaining refinement: `packages/app-sdk/src/types.ts` doesn't yet type this affordance on `AppContext`; each app currently types it locally rather than importing a shared SDK type. |
